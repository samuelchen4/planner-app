# Backend plan (`planner-backend`)

How the backend gets built, in order. Each step ends with something you can check.

## The pieces

```
             ┌──────────────── Postgres (Supabase) ────────────────┐
             │ tasks · habit_days · external_events (+ auth.users)  │
             └──▲─────────────────────────────────┬─────────────────┘
                │ writes                          │ logical replication
          ┌─────┴──────────────┐           ┌──────▼──────────┐
          │ planner-backend    │           │ PowerSync Cloud  │  sync rules: each user
          │ Hono on Cloud Run  │           │                  │  gets their own rows
          │ /sync/upload  /mcp │           └──────┬──────────┘
          │ Siri routes        │                  │ streams changes down
          │ Google worker      │                  ▼
          └─────▲──────────────┘      ┌──────── apps (iPhone, later web) ───────┐
                │ queued local writes │ local SQLite (PowerSync); reads only it  │
                └─────────────────────┴──────────────────────────────────────────┘
```

- **Supabase:** managed Postgres plus Auth. The app signs in with Supabase Auth (Sign in with Apple and Google), and its token is accepted by PowerSync and the API.
- **PowerSync Cloud:** streams each user's rows to their devices. Start on the free tier; self-hosting later is a deployment change only.
- **API (Hono, Cloud Run):** receives the phone's writes, checks them and writes Postgres. It also hosts MCP, the Siri routes and the Google Calendar worker. Business logic lives here.

## Data models: who owns them

- **`planner-backend` owns the models:** Drizzle tables, one file per table, in `src/db/schema/`. Migrations are generated from them.
- **The app keeps a copy** in `apps/mobile/src/db/schema/`, kept in step by hand: change the backend first, then copy. The app's copy currently leads, so the backend starts from it.
- **Later:** move the models into a shared `planner-utils` package/repo (like ezee-platform-utils) that both repos install. That removes the copy.
- **Schema changes are two-step** (from CLAUDE.md): add the new thing, and remove the old one only after old app versions are gone.

## Repo layout

```
planner-backend/
  src/
    db/schema/        the models (tasks.ts, habit-days.ts, external-events.ts, columns.ts)
    db/client.ts      Drizzle client (postgres-js)
    auth.ts           checks Supabase sign-in tokens (JWKS)
    routes/sync.ts    POST /sync/upload  (PowerSync uploads)
    routes/siri.ts    Siri App Intents endpoints (later)
    mcp/              MCP server at /mcp (later)
    workers/google/   Google Calendar sync + webhooks (later)
    index.ts          Hono app
  supabase/
    config.toml       local Supabase (Docker) settings
    migrations/       SQL migrations generated by drizzle-kit (prefix: supabase)
    seed.sql          local test data
  powersync/
    sync-rules.yaml   which rows go to which user
  infra/              Pulumi (Cloud Run, Scheduler, Secret Manager…)
  drizzle.config.ts
  Dockerfile
  .github/workflows/  CI: test, migrate, deploy
```

## Steps

### 1. Repo and local database
- Create `planner-backend`: TypeScript, pnpm, Hono, Drizzle, drizzle-kit, Vitest.
- `supabase init` + `supabase start` runs a local Postgres + Auth in Docker.
- Copy the models in from the app. drizzle-kit generates the first migration; `supabase db reset` applies it.
- **Done when:** the local database has `tasks`, `habit_days` and `external_events` with the right columns, foreign keys and indexes.

### 2. Access rules (RLS)
- Turn on Row Level Security for every table, with policies that only allow rows where `user_id = auth.uid()`. Drizzle can declare these next to the tables (`pgPolicy`, `drizzle-orm/supabase`), so they live in the model files.
- `user_id` gets a foreign key to `auth.users`.
- **Done when:** a test signed in as user A can't read or change user B's rows.

### 3. Auth
- Supabase Auth with **Sign in with Apple** (required by Apple if we offer Google) and Google.
- App: a sign-in screen, the session stored on the phone, and sign-out. `user_id` 'me' becomes the real user id.
- Needs: Apple Services ID / key for Sign in with Apple; a Google OAuth client.
- **Done when:** you can sign in on the phone and the app knows your user id.

### 4. Sync down (PowerSync)
- Create a PowerSync Cloud instance and connect it to Supabase. That needs logical replication (Supabase has it), a `powersync` publication and a role.
- Point PowerSync at Supabase Auth (JWKS) so it accepts the app's tokens.
- Sync rules (first version):
  ```yaml
  bucket_definitions:
    user_data:
      parameters: SELECT request.user_id() AS user_id
      data:
        - SELECT * FROM tasks WHERE user_id = bucket.user_id
        - SELECT * FROM habit_days WHERE user_id = bucket.user_id
        - SELECT * FROM external_events WHERE user_id = bucket.user_id
  ```
- App: `db.connect(connector)`; watch tables and reload the in-memory copies when another device changes them; wipe the local sample data first (its ids aren't uuids).
- **Done when:** a row inserted in the Supabase dashboard appears on the phone.

### 5. Sync up (the upload endpoint)
- App connector `uploadData`: sends PowerSync's queued changes (`PUT` / `PATCH` / `DELETE` per table and id) to `POST /sync/upload` with the user's token.
- API: check the token; allow only our tables and known columns; force `user_id` to the signed-in user; apply the batch in one transaction.
  - A change that can never succeed (invalid data) must be acknowledged and logged, not retried forever, or it blocks the queue. Only retryable failures return an error.
- Conflicts: last write wins per field (the default); stricter rules per table later if needed.
- **Done when:** a change on the phone shows up in Postgres, and on a second device.

### 6. Deploy
- Two Supabase projects, **dev** and **prod**, and a PowerSync instance for each.
- Pulumi: Cloud Run service, Artifact Registry, Secret Manager (database URL, keys), service accounts.
- GitHub Actions: on PR, typecheck and tests (against a local Supabase); on main, apply migrations to dev and deploy; prod on release tags.
- App: the API and PowerSync URLs per build profile (development/preview → dev, production → prod).
- **Done when:** the phone syncs through the deployed dev backend.

### 7. Features on top
- Google Calendar: read-only mirror into `external_events`, with webhooks and renewal on a schedule (see `google-calendar-integration.md`).
- MCP server at `/mcp`, so ChatGPT and Claude can read and edit tasks through the same rules.
- Siri: App Intents (Swift module in the app) calling the API.

## Open decisions
- **Reminders:** push notifications from the server (needs APNs credentials) or notifications scheduled on the phone. Decide before building reminders.
- **Account deletion:** Apple requires it in-app. Plan an endpoint that deletes the user and all their rows.
- **PowerSync Cloud vs self-hosted:** start on Cloud; revisit on cost.

## Accounts needed
- Supabase (free tier): dev and prod projects. **Needed at step 1** (local works without it; dev project by step 4).
- PowerSync Cloud (free tier): **step 4**.
- Apple: a Services ID and key for Sign in with Apple. **Step 3**.
- Google Cloud project: an OAuth client (step 3); Cloud Run, Pulumi state and Secret Manager (step 6).
